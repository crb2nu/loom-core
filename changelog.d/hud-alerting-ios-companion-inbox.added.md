- **Server-backed alert inbox and auto-fix decisions in the iOS companion** (`apps/loom-companion-ios/`): the app now consumes all five `/api/mobile/v1` alerting routes registered by `internal/hud/domain/alerting` — previously it had zero callers and rebuilt its inbox from SSE alone, losing every alert on relaunch. `AlertsViewModel` reads `GET /alerts` for history and merges live SSE on top (a `pipeline.alert` event carries the store's own record, so live and stored copies dedupe by id instead of double-listing), and it reads `GET /autofix/proposals` for pending fixes. There is now one read state, not two: for server-backed alerts `isRead` *is* the server ack, so marking one read POSTs `/alerts/{id}/ack` optimistically and rolls back on failure, and an ack made in the web HUD wins on reload. Approve/Reject on auto-fix proposals go through `POST /autofix/proposals/{id}/approve|reject` behind confirmation dialogs whose copy states what the HUD executor actually does — including that the `retry` strategy is still a no-op placeholder that never re-runs a pipeline. `approve` is the one admin-gated mobile route, so `APIClient` attaches `X-Admin-Token` for it.
- **Revived the alert inbox surface and the `loom://alert/<id>` deep link** (`apps/loom-companion-ios/`): `AlertsListView` was fully built but orphaned when the Alerts tab was replaced by Spawn. It is now presented as a sheet from the Dashboard, reached from the `INBOX` header, the critical-alert hero card, the `alert` attention lane, and the `loom://alerts` / `loom://alert/<id>` links — the last of which scrolls to and highlights the target alert instead of dumping the operator on the Dashboard. Docs updated: `docs/MOBILE_COMPANION_API.md` documents the bare-JSON (non-envelope) contract, the ring-buffer alert store, ack-does-not-delete, and the append-only proposal list; `docs/deep-links.md` records the restored routes.
