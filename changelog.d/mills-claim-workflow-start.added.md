- **mills: `ClaimWorkflowStart` — the S7 transactional start kernel for imperative runs** (`pkg/mills/store/dao_workflow_start.go`, migration 019). A backlog item whose policy froze an imperative template selection now starts through a kernel mirroring `ClaimPipelineStart`: queued→running CAS, budget admission against the SHARED pipeline tier, an imperative `workflow_runs` row stamped with the frozen identity verbatim, a budget reservation, and the exactly-once `workflow_start` aggregate transition — deliberately no pipeline run and no dispatch intent (the workflow scheduler discovers running imperative runs directly). Migration 019 makes `pipeline_budget_reservations.run_id` and `pipeline_transitions.run_id` polymorphic across both lanes, and the pipeline claim's reservation sum now LEFT JOINs both run tables so concurrent pipeline + imperative claims cannot jointly oversubscribe the daily cap (proven both directions by test). Terminal settle is folded into the run lifecycle CAS transaction: reservation released + item escalated (`workflow_terminal` transition) atomically — with the active reservation as the claim-provenance discriminator, so canary/admin runs that merely reference a backlog id can never release or escalate an item they did not claim; pause does not settle, and double-terminalization is idempotent. The reconciler consults an injected `WorkflowSelector` (registry-backed adapter in the operator, SquadRouter pattern) exactly once before the pipeline claim: no selection keeps the DAG path byte-identical, a held selection (workflows disabled / invalid template) skips fail-closed rather than silently falling back to the DAG, and infrastructure errors defer. Every terminal outcome escalates rather than merges: v1 registry templates stop pre-merge, so completed work products await human review. Dormant in production behind `workflows.enabled: false`. Completes S7 and the `.loom/134` dynamic-workflows plan.
