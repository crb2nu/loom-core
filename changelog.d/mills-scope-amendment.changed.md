Mills pipeline: a `scope`-only gate failure at `post_implement_gate` is now resolved by amending the backlog item's declared slice scope instead of respawning the implementer. When every violating file shares a directory ancestor of at least `pipeline.scope_amendment.ancestor_depth` (default 2) segments with a file the item already declared — and none is a protected path — the runner CAS-appends those files to the item's slices, records the gate as passed with a `scope amended: …` reason, emits `pipeline.gate.scope_amended`, counts `mills_scope_amendments_total{decision}`, and continues on the existing diff. Retry could never converge on these files (the implementer needs them, so a fresh spawn reaches for them again), which is why 20 of 25 runs escalated on 2026-07-26 against a 95.7% gate pass rate. When the reach is NOT admissible the gate stays strict: it gets one self-correction respawn instead of the full attempt budget, then escalates with a `[class=config]` marker (previously "unclassified", so auto-requeue skipped it), a structured `scope_violations` run artifact carrying the per-file rule verdicts, and a best-effort **Draft** rescue MR over the run's branch so the diff is visible rather than stranded. The amendment is default-ON (`pipeline.scope_amendment.enabled`), never weakens any other gate's judgement of the same diff, and leaves non-scope gate-cap escalations unchanged.
