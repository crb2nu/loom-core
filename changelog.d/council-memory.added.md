- **Council durable cross-run memory, default OFF behind `LOOM_MILLS_COUNCIL_MEMORY`** (`pkg/mills/store/migrations/018_council_memory.sql`, `pkg/mills/store/dao_council_memory.go`, `pkg/mills/council/memory.go`, `pkg/mills/runner/memory.go`, `pkg/mills/clients/council.go`, `cmd/loom-mills-operator/main.go`, `docs/JOURNAL_ENGINE.md`). The council recompiled a fresh brief every tick and remembered nothing of its own past deliberations — `brief.Compile()` truncates from the tail, so the oldest context silently vanished rather than being carried — which is a direct cause of reworded re-mints of themes an earlier run already minted or the mutator already refused. The council lane now owns one durable `journalengine.Journal` (`store.CouncilMemoryDAO`, one row keyed by the fixed lane id `council`, same 256 KiB cap and `Err*TooLarge` refusal semantics as the per-item memory in migration 017; deliberately *not* named a journal DAO, because migration 004 and `pkg/mills/workflow/journal_dao.go` own that word for the exactly-once workflow effect ledger). `Runner.recordCouncilMemory` appends exactly one turn per non-dryrun run, at the point where everything the run did is already durable (artifacts on disk, verdict persisted, mutations applied or deliberately skipped) — the same discipline that puts `recordItemMemory` after `PutStage`, so the journal can never claim work the audit trail lacks. The recorded turn is journal-derived end to end: the epoch is the entry count and the displayed run ordinal is the turn count, never a clock reading and never the run id, because one volatile byte above the now-block boundary is the silent failure that drops the prefix-cache hit rate to zero. The composed outcome is minted item ids + titles, plan-lane routing, dedup and gray-band refusals with their Jaccard scores, the quality gate's score/partial verdict, and the mutator's disposition — mints first, so the 8 KiB tail truncation costs the trailing sections rather than the thing a later tick most needs. Every failure path logs and returns: a memory write never fails a run that already produced artifacts.
- **Council memory renders into the stable half of the editor prompt, above the churning sections** (`pkg/mills/clients/council.go`, `council_anthropic.go`, `council_openai.go`). `buildCouncilEditorPromptParts` now takes a memory render and emits it stability-ordered — constant preamble + guardrails → append-only memory → repo-tree digest + pattern catalog → volatile brief — so it rides the Anthropic backend's `cache_control`'d system block and the OpenAI backend's `prompt_cache_key`'d static prefix. The **kill-test** (`pkg/mills/clients/council_memory_prompt_test.go`) renders the stable half across four simulated ticks with a growing memory and asserts `journalengine.CheckPrefixExtension`, plus a repo-tree-churn case; `pkg/mills/runner/memory_test.go` makes the producer-side assertion across three real council runs. Measured result: the memory block and everything above it is a strict prefix extension across ticks *and* survives a repo-tree change, which is what the ordering was chosen to buy — but because the memory grows in the middle of the stable half, the small fixed-size repo digest and pattern catalog below the append point re-prefill each tick, so the *whole* stable half is not one prefix extension. Placed after the repo digest instead, the whole stable half would match within a commit and go fully cold on the next, and a commit between two council ticks is the normal case. With the flag off the editor prompt is byte-identical to the previous one (asserted), and a nil, empty, or failing memory loader renders nothing rather than blocking a run. Spinning Room frames deliberately get no memory: a frame is a different lane that never records into this journal.
