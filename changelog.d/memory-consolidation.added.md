- **Make the item-memory size cap observable, and pre-wire the consolidation response** (`pkg/mills/pipeline/item_memory.go`, `pkg/mills/pipeline/memory_consolidator.go`, `pkg/mills/metrics.go`, `cmd/loom-mills-operator/config.go`): a per-backlog-item memory journal that grows past half the 256 KiB row cap now logs `item memory: snapshot over soft threshold` and increments `mills_item_memory_soft_threshold_total` at record time — unconditionally, so "the cap is biting" is visible while writes still succeed instead of only at the hard refusal, where an item's memory stopped growing silently. The response is wired but dark: with `LOOM_MILLS_MEMORY_CONSOLIDATE` set, a crossing record distils the oldest half of the journal through a `journalengine.Consolidator` served by the operator's instrumented client (llmusage component `mills-memory`, model `FLEXINFER_MEMORY_MODEL`, default the weaver/research model) before persisting, at most once per record, counted by `mills_item_memory_consolidations_total`. A consolidator failure or empty answer leaves the journal completely untouched and persists it unconsolidated, exactly as before the change.
